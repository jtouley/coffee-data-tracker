# Shopify storefront 429/503 waves: what they mean and how to get full catalogs legitimately

Researched 2026-10-31. Sources are docs, changelogs, forums and blogs only: no request went to any store or Shopify
storefront. Labels: **[Shopify doc]** = shopify.dev/shopify.com documentation or changelog; **[Shopify staff]** =
a named Shopify employee on a forum (official in voice, not documentation); **[Anecdotal]** = forum users and third
parties; **[Google doc] / [Cloudflare doc]** = those vendors' docs. "Undated" = the page shows no date; read on
2026-10-31.

## Summary: recommendations ranked by data gain per unit of complexity

1. **Give the crawler a dedicated static egress IP** (Cloud Run Direct VPC egress + Cloud NAT with a reserved IP). Cloud Run's default egress is a shared Google pool; Shopify staff (2026-10-30) said shared egress gets challenged because of *other tenants'* traffic and called dedicated egress "the safest workaround for now". Low effort, likely the largest single gain.
2. **Treat a block as platform-wide, and stop.** The limits behave per client IP across all Shopify stores, not per store. On a 429/430/503 from any store, pause all Shopify work and honor `Retry-After` (60 s is typical on 429s). Shopify staff asked crawlers to "stop on 429s" and not to try to solve challenges. `PlatformLimiter` already does this. Keep it, and don't let the fallback path start fresh requests during a pause.
3. **Tell a challenge from a rate limit, and log what Support needs.** Record status, `server`, `cf-mitigated`, `content-type`, `retry-after`, `cf-ray` and `x-request-id` for every block. A Cloudflare challenge comes back as HTML (`cf-mitigated: challenge`) with a 429, 403 or 503 status. It's about the IP's reputation, so slowing down doesn't clear it; back off for much longer. Without these headers we can't tell which 503s were challenges.
4. **Sign every request with Web Bot Auth, then file Shopify's higher-limits form.** This is the route Shopify documents (changelog 2026-05-07): unsigned bots get the strictest limits. Medium effort: an Ed25519 key, a key directory on our domain, and a `Signature-Agent` sent as a quoted string. Forum reports show that a signature alone isn't recognized until the bot is registered, and that registration takes days to weeks.
5. **Send fewer requests per product.** `/products.json?limit=250&page=N` returns 250 products per request. Use the sitemap/`.js` fallback only for stores where `products.json` fails, and only for products whose sitemap `<lastmod>` changed since our last good copy. That cuts the fallback's request count, which is where the 503s hit.
6. **Spread the run over a window, serially per store.** Run at a low global rate, one store at a time, in shuffled order across hours instead of a 20-minute burst. Practitioners report that bursts trip the limit and spacing does not (anecdotal; Shopify publishes no numbers).
7. **Try conditional requests at no cost.** Send `If-None-Match`/`If-Modified-Since` when we hold an `ETag`/`Last-Modified`. Shopify storefronts have been seen sending `etag: "cacheable:…"` (2024), but nothing documents 304 support on `products.json`. Measure it from our own logs.
8. **Identify honestly.** Keep the UA `coffee-data/0.1 (+URL)`, and add a contact email and a bot page that explains the purpose, the rate and how to opt out. Shopify staff asked crawler operators to "correctly advertise your User-Agent (do not hide it)".
9. **Ask the roasters who opt in for a merchant-minted Web Bot Auth signature** (Shopify admin, since 2025-08-29). Shopify built it so merchants can authorize tools "without being blocked". It gives full fidelity for those stores, but coverage grows only as roasters opt in.
10. **Avoid tokenless Storefront API, Catalog/UCP MCP and the Ajax `.js` API as primary sources.** The Shopify API Terms (updated 2026-10-07) bar using the Shopify API "to build any commerce or product index" and bar systematic data collection without the merchant's grant. The Catalog docs forbid caching results, and the Ajax API is documented for Shopify-hosted themes. Get a legal read before relying on any of them.

## 1. What 429, 503 and 430 mean on online-store endpoints, and their scope

### Status codes

| Code | What Shopify says | Label / source / currency |
|---|---|---|
| 429 | "The request wasn't accepted because the app has exceeded the rate limit." The GraphQL Storefront/Admin APIs instead return `200` with a `THROTTLED` error. | [Shopify doc] https://shopify.dev/docs/api/usage/response-codes (undated) |
| 430 | "Shopify Security Rejection: the request wasn't accepted because it might be malicious, and Shopify rejected it to protect the app." The Storefront API docs: "If a request appears to be malicious, Shopify responds with a `430 Shopify Security Rejection`." | [Shopify doc] same page; https://shopify.dev/docs/storefront-api (api_version 2026-10) |
| 503 | "The server is currently unavailable." Nothing more. Shopify documents no bot-related meaning for 503. | [Shopify doc] https://shopify.dev/docs/api/usage/response-codes |
| 423 / 403 | 423: "The shop isn't available. This can happen when stores repeatedly exceed API rate limits or due to fraud risk." 403: store marked fraudulent. | [Shopify doc] https://shopify.dev/docs/storefront-api |

### Bot limits on online-store pages (documented)

- **2026-05-07 (effective 2026-05-30):** "Shopify now applies stricter rate limits to bots and agents that access the Storefront API and Shopify-hosted online store pages. Bots and agents that don't sign their requests are subject to the strictest limits. To qualify for higher rate limits, operators should sign their requests with Web Bot Auth. If you require higher rate limits than those provided to Web Bot Auth traffic, please contact us through this form [https://forms.gle/V88RD31uAVirqE4e9]." The changelog doesn't name `products.json`, sitemaps or `.js`. They are online-store pages, so the change covers them. [Shopify doc] https://shopify.dev/changelog/posts/bots-and-agents-should-identify-themselves-via-web-bot-auth
- Storefront API: buyer traffic has no fixed request-per-minute limit, "Bots and crawlers are limited, most strictly when unsigned", and "Signed traffic is subject to higher rate limits than anonymous traffic." [Shopify doc] https://shopify.dev/docs/storefront-api (2026-10)
- "Shopify may temporarily reduce API rate limits to protect platform stability." Recommended backoff is one second (general guidance, not storefront-specific). [Shopify doc] https://shopify.dev/docs/api/usage/rate-limits (undated)
- **No published numbers.** Shopify documents no rate for `/products.json`, `/products/<handle>.js|.json`, sitemaps or collection pages. In 2025 a Shopify staff member said there is "room for improvement in our docs around rate limits", and that "There isn't currently a process to whitelist a store or specific theme." [Shopify staff] https://community.shopify.dev/t/bug-429-page-errors-are-too-aggressive/14325 (Apr–Jul 2025)
- Ajax API: "There are no hard rate limits on the Ajax API. It's still subject to Shopify's standard API abuse-prevention measures." [Shopify doc] https://shopify.dev/docs/api/ajax (undated)

### Per store, per IP or platform-wide?

Shopify doesn't document the scope. The evidence points to **per client IP or network, applied across all Shopify
stores at the edge**, with no per-store bucket:

- A crawler on Oracle Cloud got 429s on its first request to all ~40 stores, at any hour, for 7+ days, while the same requests from a residential IP got 200. The poster: "no recovery after 7 days, so not a rate-limit bucket". [Anecdotal] https://community.shopify.dev/t/signed-web-bot-auth-crawler-gets-429-on-every-request-from-oci-since-2026-09-29/38335 (2026-10-06/09)
- On a similar OCI case, Shopify staff said the request hit "standard automated-traffic protections… This points away from a conventional rate-limit bucket", and "We don't currently document a supported process for registering a crawler egress IP." The case concerned coffee stores (coffeebeancorral.com and others): 0/28 from OCI, 28/28 residential. [Shopify staff] https://community.shopify.dev/t/third-party-web-bot-auth-crawler-receives-immediate-429s-from-oci-but-succeeds-residentially/36440 (2026-07-31; access came back about a week later, cause unconfirmed)
- **Closest to our setup (shared cloud egress):** a crawler on Cloudflare Workers' shared egress got a 429 Cloudflare "Verifying your connection…" HTML page on `/products/<handle>.json` across stores, with no `retry-after`. Shopify staff: "Cloudflare generated the 429 challenge before the request reached Shopify"; "The shared Workers path had already been placed into a challenge period by other traffic, and the bot's request rate did not cause the challenge"; "known edge limitation". They recommended dedicated egress as "the safest workaround for now", and asked the bot to keep honoring robots.txt, stop on 429s, and not try to solve or bypass the challenge. [Shopify staff] https://community.shopify.dev/t/signed-web-bot-auth-crawler-receives-cloudflare-challenge-page-instead-of-rate-limit/39056 (2026-10-30)
- Shopify staff: "The 429 is the stricter rate limit Shopify applies to bot traffic that isn't recognized as verified." Signing alone isn't enough; the crawler must register through the form. [Shopify staff] https://community.shopify.dev/t/third-party-web-bot-auth-request-still-receives-429-across-shopify-storefronts/38215 (2026-10-09; thread open on 2026-10-30)
- 430s from Google Cloud Functions and Cloud Run: Partner Support blamed "the use of a shared IP on the app's hosting service". Static IPs or VPC egress helped some posters, not all. [Anecdotal, relaying Shopify Partner Support] https://community.shopify.com/t/surge-in-430-status-code-inspite-of-using-buy-identity-header/240616 (2023-08 to 2024-03; old, and about the API)
- Google's own crawlers (ASN 15169, rotating IPs) reportedly see high `shopify-complexity-score` values on first requests. The poster's hypothesis is unverified, and another user disputed it. The header is undocumented. [Anecdotal] https://community.shopify.com/t/technical-shopify-bot-detection-complexity-score-permanently-blocks-google-search-console-sitemap-crawler-reproducible-with-asn-15169-ip-rotation/608454 (2026-04-20). Our Cloud Run default egress is drawn from Google's shared pool: [Google doc] https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip (undated)

**What our 503 waves most likely are (inference, not documented):** we see 503s across many stores from one IP,
sometimes on the first request. That fits an edge mitigation (Cloudflare challenge or block) aimed at the IP or
network, not a per-store overload. A third-party crawler guide says "a 403, or a 503 with a Cloudflare challenge, is
bot protection" and "slowing down will not help" [Anecdotal] https://docs.squirrelscan.com/guides/rate-limited-hosts
(undated). Cloudflare documents the marker: a challenge response "will have the `cf-mitigated` header present and
set to `challenge`" and is always `text/html` [Cloudflare doc]
https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/ (undated).
Logging these headers would confirm it.

### Retry-After

- Shopify's docs don't mention `Retry-After` for storefront responses. [Shopify doc] https://shopify.dev/docs/api/usage/response-codes
- Seen in practice: Shopify's 429 on `products.json` carries `retry-after: 60`, sometimes from the first request ([Anecdotal] threads 38335, 38215, and https://community.shopify.dev/t/persistent-cloud-server-429s-despite-web-bot-auth-setup/38585, 2026-10). The Cloudflare challenge 429 had **no** `retry-after` (thread 39056). 430s are reported without `Retry-After` (thread 240616, 2024).
- The 60 s value can understate the block: the OCI blocks lasted days. That matches our existing `give_up_after` design.

## 2. Official or sanctioned ways to read a public catalog without the merchant's credentials

| Route | What it is | Eligibility / terms | Fit for registry.coffee |
|---|---|---|---|
| **Storefront API, tokenless** | `POST https://{shop}/api/2026-10/graphql.json` without a token. Covers products, collections, search, pages and cart. Query complexity is capped at 1,000. Product **tags**, metafields/metaobjects, menus and customers need a token. Bots are rate-limited, most strictly when unsigned. [Shopify doc] https://shopify.dev/docs/storefront-api (2026-10) | Shopify API Terms: "By accessing or using the Shopify API, you agree…". §2.3.14: "not use the Shopify API to conduct any systematic or automated data collection activities… [or] to build any commerce or product index". §6.1.1: the merchant must grant the developer access first. [Shopify doc] https://www.shopify.com/legal/api-terms (updated 2026-10-07) | Technically complete except tags, which we use. On a plain reading of the Terms, using it for a cross-store index without merchant grants is prohibited. Get legal review before any use. |
| **Storefront Catalog MCP (UCP)** | `POST https://{store}/api/ucp/mcp`, tools `search_catalog`, `lookup_catalog` (≤10 IDs), `get_product`. Needs an agent profile URL in `meta.ucp-agent.profile`, no API key. Returns variants with sku, price, availability and tags. [Shopify doc] https://shopify.dev/docs/agents/catalog/storefront-mcp (undated) | The catalog/cart tools on the older `/api/mcp` moved here [Anecdotal] https://craftshift.com/?p=24004. Built for agents shopping one merchant. | The same API Terms apply. It's a shopping agent interface, not a bulk export. |
| **Global Catalog MCP** | `https://catalog.shopify.com/api/ucp/mcp`, products from "any eligible merchant", clustered by UPID. Agent profile, keyless. [Shopify doc] https://shopify.dev/docs/agents/catalog (undated) | "Caching results isn't allowed." Images must be "rendered in real-time (not downloaded to servers)". Some fields are AI-"Inferred". "Keyless catalog access doesn't support rate limit increases." Some secondary sources say access opened to all developers in 2026: [Anecdotal] https://stellagent.ai/insights/shopify-spring-26-agentic-commerce-developers. The old REST Catalog API is deprecated: [Shopify doc] https://shopify.dev/docs/api/catalog-api | The no-caching rule rules out a weekly dataset. It could serve live lookups or discovery of new roasters. |
| **Ajax API `.js`** | `/products/<handle>.js`, max 250 variants, presentment currency. [Shopify doc] https://shopify.dev/docs/api/ajax | "The Ajax API can only be used by themes that are hosted by Shopify." | Documented for themes, not third parties. |
| **Merchant-minted Web Bot Auth signatures** | Merchants create signatures in the Shopify admin to "authorize your own crawlers, scripts, or tools to access your public Shopify online store… without being blocked". The tool sends `Signature-Input`, `Signature` and `Signature-Agent`, which expire on a date the merchant sets. Intended uses include third-party tools for "data analysis". [Shopify doc] https://changelog.shopify.com/posts/authorize-custom-crawlers-and-tools-with-new-crawler-access-keys (2025-08-29) | Needs each roaster's cooperation. Merchant-minted signatures carry `Signature-Agent: "https://shopify.com"` [Anecdotal] https://community.shopify.dev/t/web-auth-auth-valid-signatures-not-accepted/36894 (2026-08) | The cleanest full-fidelity route for opted-in roasters. |
| **Web Bot Auth (our own identity) + higher-limits form** | Sign per the IETF draft https://datatracker.ietf.org/doc/draft-meunier-web-bot-auth-architecture/. Enrolling with Cloudflare isn't required. [Shopify doc] changelog 2026-05-07 | Shopify staff: "a valid signature alone doesn't establish that Shopify recognizes your bot's identity". The form "is for higher limits than those already available to signed traffic". Support may require an affected store owner to contact them. [Shopify staff] thread 38585 (2026-10-15/16) | The documented route for our existing `products.json` crawl. |
| **robots.txt** | Shopify generates a default file "that works for most stores", and merchants can override it with `robots.txt.liquid` [Shopify doc] https://shopify.dev/docs/storefronts/themes/seo/robots-txt (undated). Since July 2025 a header comment says "Automated scraping, 'buy-for-me' agents, or any end-to-end flow that completes payment without a final review step is not permitted" in the context of checkout. Shopify's Ilya Grigorik said it adds no rules, just "a comment for curious humans" [Anecdotal/press] https://www.modernretail.co/technology/shopify-has-quietly-set-boundaries-for-buy-for-me-ai-bots-on-merchant-sites/ (2025-07-14). The current managed default also points to `/agents.md` and the UCP/MCP endpoints, and disallows `/cart.js`, `/sf_*` and others. No `.json` or product disallow is reported [Anecdotal] https://community.shopify.dev/t/robots-default-groups-returns-an-older-rule-set-than-the-robots-txt-shopify-serves-by-default/38352 (2026-10-06). Some merchants add `Disallow: /*.json` [Anecdotal, third-party scraper docs]. | Advisory. We already honor it per store. | Keep honoring it per store, `.json` rules included. |
| **Verified-bot programmes** | Shopify points to Web Bot Auth plus its form. In 2025 Shopify staff also suggested applying to Cloudflare's verified bots registry [Shopify staff] thread 14325 (2025-05-07). | Cloudflare's programme has its own criteria. | Secondary option. |
| **Shop app / feeds** | I found no public, crawler-facing product feed from Shopify or the Shop app. Merchant feeds to Google and others aren't public. | — | Not available. |

## 3. Best practice for avoiding 429/503 waves on storefronts

| Practice | Evidence | Label |
|---|---|---|
| **Stable, dedicated egress IP** | Shopify staff called dedicated egress "the safest workaround" for challenges on shared egress (thread 39056, 2026-10-30). Static IPs fixed 430s for some GCP users, not all (thread 240616, 2024). Setup: reserve an IP, Cloud NAT, Direct VPC egress "all traffic" [Google doc] https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip. One IP is a stable identity, not a disguise. Don't rotate IPs to dodge limits. | Shopify staff + Google doc |
| **One global budget for all Shopify stores; serial, spaced requests** | Limits act per IP across stores (§1). A crawler guide: "One request at a time to each host, half a second apart", and audit storefronts one after another, not in parallel (squirrelscan, undated). Our own 2026-10-28 run broke at more than 4 req/s with 32 workers (`src/coffeedata/ratelimit.py`). Shopify staff in 2025: "implement pacing on your crawl rate". | Anecdotal + Shopify staff |
| **Stop on 429, honor Retry-After, back off long on challenges** | "stop on 429s" and don't solve challenges (staff, 2026-10-30). The 1 s backoff guidance is for API buckets (rate-limits doc). After 429s, users saw lockouts of an hour or more (thread 14325, 2025). | Shopify staff + anecdotal |
| **Crawl window** | Spread the weekly crawl over hours or days instead of a short burst. After ~15 hours idle, the first ~15 calls in 10 min succeeded and then 429s began (thread 14325, 2025-07-16), so the limit looks burst- or budget-based. Time of day made no difference for an IP-reputation block (thread 38335). | Anecdotal |
| **Spread across stores vs batch per store** | Under an IP-wide limit, the total rate is what counts. Finishing one store before starting the next keeps each store's pages together and keeps concurrency low. Shuffle the store order so the same stores aren't always last. | Inference from the above |
| **Honest UA with contact** | "correctly advertise your User-Agent (do not hide it)" (staff, thread 14325, 2025-05-07). One crawler moved from a browser UA to `GudValBot/1.0` while registering (thread 39056). | Shopify staff |
| **Conditional requests / caching** | Undocumented. A merchant saw `etag: "cacheable:…"`, `x-cache: hit, server` and `cf-cache-status: DYNAMIC` on storefront responses (2024-09) [Anecdotal] https://community.shopify.com/t/shopify-cache-cdn-update-inquiry/357196. No source confirms 304s on `products.json`. Sending `If-None-Match` is harmless; log the share of 304s. | Anecdotal |
| **Fewer requests** | `limit=250` is the maximum ("silently clamped to 250", default 30). Paging stops past page × limit = 25,000 with HTTP 400 "Page * Limit exceeds the 25000 limit" [Anecdotal, vendor-authored] https://dev.to/odeeb/shopify-productsjson-pagination-250-limit-and-the-25000-cap-1g37 (2026-09-29). Sitemap product entries carry `lastmod` [Anecdotal] https://www.semrush.com/blog/shopify-sitemap/. Refetch only changed products on the fallback. | Anecdotal |
| **Keep diagnostics** | Shopify staff ask for UTC timestamp, `x-request-id`, `cf-ray`, full headers and source IP before investigating (threads 36440, 39056). | Shopify staff |
| **IPv4 on Cloud Run** | A Cloud Run user's timeouts to Shopify came from IPv6 resolution without IPv6 egress (2024). Relevant only to timeouts, not to 503s. [Anecdotal] https://community.shopify.com/t/api-throttled-when-we-are-nowhere-near-the-limit/302658 | Anecdotal |

## 4. Do `/products.json?page=`, `/collections/all/products.json` and `/products/<handle>.json` behave differently from `.js` under limits?

- **No documented difference.** All are online-store pages behind the same edge, so the 2026-05 bot limits cover them all (changelog). Shopify publishes no per-endpoint limits. [Shopify doc]
- **The same block hits all of them:** 429s in the forum reports hit `/products.json?limit=1` (38335, 38215), `/collections/<handle>/products.json?limit=250&page=1` (36440) and `/products/<handle>.json` (39056). No report found a variant that escapes a block. [Anecdotal]
- **The difference is cost per product:** one `products.json` page holds up to 250 products, while `.js`/`.json` per product is one request per product. Under an IP-wide budget, the bulk endpoints are 100–250× cheaper. That is why the fallback path (sitemap plus one request per product) hits blocks first.
- **Fidelity differences:** `.js` returns prices in the presentment currency, uses `description` instead of `body_html`, and is capped at 250 variants [Shopify doc] https://shopify.dev/docs/api/ajax/reference/product. `products.json` returns `body_html`, tags, variants with `available` and `compare_at_price`, but no currency field [Anecdotal] https://dev.to/mersetti/track-competitor-prices-on-any-shopify-store-with-productsjson-and-catch-restocks-39k8. Some stores disable `products.json` on their main domain, which is when a sitemap fallback is needed [Anecdotal, same source and Apify actor docs].
- **Paging:** collection endpoints have the same 250/25,000 limits (dev.to 2026-09-29, anecdotal). Use them to get past 25,000 products in big stores, and deduplicate by product ID. Not relevant for roasters.

## Out of scope, and not recommended

Rotating IPs or proxies to spread load, browser impersonation, and solving or bypassing challenges are excluded by the
brief. Shopify staff explicitly asked crawlers not to do the last of these (thread 39056).
