# Batch commits for the weekly crawl: evaluation and prototype
- **The proposal already exists.** `ingest.run` commits the manifest first, then every 200 roasters (`CHUNK`, one HF commit each). Last night's run (Actions 41111000693, cancelled at 4h00m) left 6 commits on HF (checked read-only): the manifest plus 5 chunks, 1,000 of 2,545 roasters. It lost at most the last unfinished chunk (about 32 min of work). The cause was speed, not missing commits: 180 Shopify 429 pauses (each stops all Shopify requests for 60 s) dropped the rate to 0.38 req/s, so each chunk took about 40 min.
- **The real gaps.** (1) `weekly --run-date` defaults to today, so re-running the next day starts a new run_date: 2026-10-30 stays partial for good, 1,000 roasters get an extra week one day later, and the gate only ever judges the new run. (2) A chunk is flushed by count only, so a slow crawl can lose about 40 min of work. (3) A timeout kills the job before it can stop cleanly.
- **Recommended design.** Keep a commit per chunk. One commit at the end plus a local checkpoint can't work: the Actions runner's disk is gone after a timeout, so staging can't serve as the checkpoint. Flush at 200 roasters or 10 min, whichever comes first (about 13–25 commits a run). Stop fetching at 170 of the job's 240 min: publish and exit non-zero before the build. Resume: without `--run-date`, `weekly` continues the latest run under its own run_date when it has a full manifest from the last 6 days with roasters never tried (`ingest.open_run`). It skips roasters already fetched OK, which existing `select_states` does; earlier failures are refetched. A catch-up schedule on Tuesday runs `weekly --resume-only`, which does nothing when no run is open.
- **How the gate treats partial runs.** `run_is_complete` (min_attempted_share 1.0) fails a partial run, so nothing is served and the current release stays. The expected set is the union of the run's full manifests, so a resumed (smaller) manifest can't shrink it. On duplicates: `stg_run_walk` counts one OK batch per roaster-week, `unique_runs` enforces that, and bodies and enrichments are deduped against the lake. Within one run_date a resume adds nothing twice. Two run_dates are the real risk, which is what `open_run` fixes.
- **HF limits.** The per-action commit quota is undocumented; the docs only say "repo commits" have their own limits ([rate-limits](https://huggingface.co/docs/hub/rate-limits)). Hitting it returns 429 "exceeded our hourly quotas for action: commit" ([forum](https://discuss.huggingface.co/t/exceeded-our-hourly-quotas-for-action-while-loading-dataset-to-hf-hub/60698)); 128/h is reported but unverified ([unofficial](https://wiki.161-35-77-84.sslip.io/lesson-hf-commit-rate-limit.html)). The API allows 1,000 requests per 5 min on a free plan and 2,500 on PRO; each publish makes about 4 calls. Repo guidance ([storage-limits](https://huggingface.co/docs/hub/storage-limits)): under 100k files, under 10k entries per folder, 50–100 files per commit, and the experience "degrades after a few thousand commits" (`super_squash_history` is the fix, and it is irreversible). Our use: about 30 commits and 60 files a week; the dataset has 64 commits and 223 files today. Commit count, including the app's commit per shot, is the long-term cost; files are not.
- **Tests** (local lake only; nothing pushed or written to HF). Crash: a child process is SIGKILLed after 17 fetches (CHUNK 5), leaving 15 roasters in the lake, and the dbt build fails `run_is_complete`. The next day `open_run` returns 2026-10-30 and the resume fetches only the other 15. Result: 30 fetch rows for 30 roasters, no 2026-10-31 run, and a dbt build that passes every gate test including `unique_runs`. `run_completeness` shows 30/30 attempted in 1 run; `stg_snapshots` has 90 rows and 0 duplicates. Further tests cover the deadline (flush, then resume to complete), the time-based flush, `open_run` edge cases (old, sample or finished runs) and weekly stopping before the build: 6 new tests, all passing. The full suite had 613 passed and 2 failures, both test stubs that didn't take `deadline`; after fixing them those files pass.
- **Memory** (fake data at real scale from the 2026-10-28 run: 2,545 roasters, 39,280 products, the real distributions of product counts and body lengths; 1 s per fetch, 32 workers). On top of 108 MB of imports: holding everything +505 MB, `main`'s 200-roaster chunks +107 MB, the prototype +102 MB. `main` already streams to disk, and memory isn't the constraint on a 16 GB runner. With instant fetches the backlog of unwritten results reaches +317 MB in either version.
- **Code size.** +139/−20 lines in `ingest.py`, `cli.py`, `weekly.yml` and two test stubs, plus a 233-line `tests/test_resume.py`. Worktree `build/crawl-plan/wt-batch`, branch `crawl-batch-checkpoint`, uncommitted.
- **Risks.** At the deadline the job still waits for fetches already running; a Shopify pause can make one take minutes, which the 70 min margin covers. A resumed run's `fetched_at` spans days under one run_date. If the catch-up run also times out, the week stays unserved, and after 6 days the open run is abandoned. Freshness fails if no full run passes within 8 days. None of this fixes the actual cause, Shopify throughput (rate, concurrency, how 429s are handled), which is the next thing to fix. Commit count keeps growing until a squash.
