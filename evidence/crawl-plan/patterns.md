# Crawl 429s: proxies, proven patterns, Shopify facts (research only; no roaster sites contacted)

**Already in the repo:** `ratelimit.PlatformLimiter` gives one shared Shopify budget (3 rps, 8 in flight). A block pauses every store, halves the rate and gives up after 900s. On top of that: per-host spacing, a checkpoint every 200 roasters (`CHUNK`), resume by `run_date`, and one `--retry-failed` pass (cli.py:387). Batch commits and a retry pass are therefore done already. What's missing is a time budget and spreading the load over more days.

## 1. IP rotation / proxies: don't
- **What a 429 asks:** RFC 6585 says the client "has sent too many requests" and "MAY include a Retry-After header indicating how long to wait before making a new request". The server decides how it identifies the client. Retrying from another IP doesn't wait; it makes the rate limit useless. Shopify's 430 says "it might be malicious" (shopify.dev/docs/api/usage/response-codes). That is a security control, not a quota.
- **Terms:** The Shopify API Terms bar circumventing limits (2.4), bypassing restrictions (2.3(9)) and circumventing "technological measures" (2.3(7)). It's unclear whether storefront `/products.json` counts as the "Shopify API", so I can't confirm a direct breach. It does break the spirit of those terms, and of the README's rule "no sites that block bots".
- **Legal:** In *Craigslist v. 3Taps* (N.D. Cal. 2013), using proxies to get past an IP block after a cease-and-desist letter was held to be unauthorized access under the CFAA. *hiQ v. LinkedIn* protects public pages only while access is open, and hiQ later lost on contract. For a public project that names itself in its User-Agent and publishes the data, rotation leaves a written trail of deliberate evasion. That trail can be used against it, and it costs credibility with roasters.
- **Blocking:** Getting blocked is likely. Shopify says it "may use any technical means" and can suspend access (API Terms 7.1), and datacenter proxy pools are exactly what its bot heuristics flag. Residential proxies mostly use other people's home connections and raise their own ethical problems. An nginx box only helps as one fixed egress; it can't help as a splitter.
- **Fixed, identifiable egress:** This helps somewhat, but not through allowlisting. GitHub-hosted runners share Azure IPs with other scrapers, and community threads blame shared IPs for 430s, so a fixed IP should mean a cleaner reputation. Shopify's operators could also identify and contact the crawler, the way Common Crawl publishes its IP ranges, reverse DNS and UA. I found no way for a merchant to allowlist an IP at Shopify's edge, and no Shopify bot-verification program, so don't count on allowlisting. Options: a self-hosted runner or small VPS with a static IP, or GitHub larger runners with static IPs (paid plans). Keep the current UA and add a contact email.
- **Recommendation:** No rotation. Keep one identifiable IP, stay inside one rate budget, honor Retry-After fully and spread the load out.

## 2. Proven patterns: what each solves here, and the cost
- **Scrapy AutoThrottle and download slots** (docs.scrapy.org/en/latest/topics/autothrottle.html): adaptive delay per slot, and a slot can be keyed by any value, not just the domain. PlatformLimiter already is a slot keyed by platform, with back-off that halves the rate on a block and recovers slowly. Latency-based tuning would add little. Cost: none; it's adopted already.
- **Nutch, StormCrawler and Heritrix per-host queues:** queues by host, domain or IP; a per-queue exception cap (Nutch `fetcher.max.exceptions.per.queue`); a retry delay of minutes (Heritrix `retryDelaySeconds`, 300 in one sample profile). This fixes "same store 429s repeatedly": after N blocks, park that host and retry it at the end of the run or the next day, rather than retrying right away inside `_send_retrying`. Cost: small, about 30 lines in http.py/ingest.py.
- **Retry-After:** honor it fully. Today the limiter caps it at 120s (`max_cooldown`), and the path without a limiter caps it at 30s (http.py `min(int(retry_after), 30)`). Both resume earlier than the server asked. If the wait is longer than the remaining time budget, defer the work instead of sleeping. Cost: small.
- **Work queue and dead-letter queue (DLQ):** the `fetches` table plus `--retry-failed` is the queue already. The missing pieces are a deadline that stops submitting new work about 30 minutes before the 240-minute job timeout, so the run ends cleanly, and a DLQ status for roasters that failed K passes in a row, which go to a later run or a person. Cost: small to medium. Parallel pools per connector add little, because Shopify is one shared budget either way.
- **Sharding the weekly crawl across days:** assign each roaster a day by `sample_key(roaster_id) % 7` and run daily, so each day sends about 520 Shopify requests instead of about 3,600. This is the biggest cut in burst size and the most robust fix, and Common Crawl and search engines all crawl continuously this way. Cost: medium to high. `run_date`, the full-mode manifest, `run_ok_rate`, the volume checks and the dbt "latest weekly snapshot" logic all assume one run per week. A cheaper step first: rerun the same `run_date` later that day or the next day (resume already works).
- **Conditional requests (ETag / If-Modified-Since, RFC 9110 §13):** a 304 saves bytes, not requests. A rate limit that counts requests probably still counts it (unconfirmed). Paged `products.json` and storing the validators make it awkward. Cost: medium, gain uncertain. Do it last, and measure first whether Shopify sends validators on `products.json`.

## 3. Shopify facts
- **Rate limit per store or per client IP:** Shopify documents no limit for storefront `/products.json` at all. A per-IP limit across stores is supported by this repo's own 2026-10-28 run (unrelated stores 429ing together) and by one scraper vendor (apify.com/rl1987/shopify-api-scraper: "per client IP, across stores"). That vendor sells proxies, so treat it as biased. Repeated 429s from one store hint at a per-store layer as well; I can't confirm either from Shopify.
- **Documented codes:** 429 is the rate limit and 430 is the security rejection (shopify.dev response-codes page). The Admin API's 40 requests per app per store per minute (leaky bucket) doesn't apply to anonymous storefront JSON. Community threads report that a 430 carries no Retry-After header.
