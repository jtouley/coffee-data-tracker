# Design A: one weekly ingest job + the proven fixes, ELT (worktree A/wt, branch arch-a, local commits, never pushed)
**Design.** origin/main 6bda240 + #62 (per-store Shopify backoff, deferred rounds) + the batch prototype (10-min/200-roaster flush, 170-min deadline, `open_run` resume) + PAGINATION v1+v2 final, 19:22 (limit 250, 60/120/240 s page backoff without holding a worker, conditional short-page stop, parked progress for `crawl-retry`) + a burst fix (only a store's first block in a run counts toward platform-wide detection; a 430 is still platform-wide). **ELT:** ingest writes only snapshots, bodies, fetches and manifests; `coffeedata enrich-pending` derives the Claude candidates after load from stg_products' logic; roaster "has coffee" comes from the build's classification in dim_roaster.sql and registry.STATE_SQL, both via the shared `products.derive`.
**Code vs 6bda240.** src +832/−112 (ELT: products.py +77, enrich +58/−42, registry +50/−1, cli +32/−3, ingest −25 net). dbt +22/−30 (owner-approved ELT: dim_roaster, the input_hash macro; stg_products moved to products.py). app/ and contracts/ 0. Tests +741/−49; full suite 676 passed after ELT, plus the 19:22 v2 body_text fix and its test. **Build diff** on a 102-store mock lake, old vs new code: all 34 models row-for-row identical, 85,623 rows. The one difference is stg_enrichments, which no longer has rules rows; no mart reads those (dim_coffee reads llm rows only).

The drill (WooCommerce 503 for 2 h, then a kill at 50% on Monday, resumed Tuesday) ended served with one run_date (run before the re-test fixes). **First-ever run, no history:** S2 failed the gate (86.4%), since without a known product count every store paginates to the empty page, which adds Shopify traffic. **Real Shopify crawl** (1,070 stores, publishing off): 55.6 → 34.8 min, 429s 1,166 → 670, platform pauses 5 → 0, ok 96.6% → 97.4%, refused 22 → 14, other failures 14 → 2 (+12 parked mid-catalog). See real.md and real2.md.
**Weaknesses.**
- One ingest job shares 32 workers and 240 min across every connector, so an IP-wide limit or a slow connector delays all of them.
- A Monday fault costs Tuesday a rerun, which redid about 400 finished roasters in the drill.
- Parked progress sits in lake.root/parked; on HF that is local staging, so on Cloud Run it is lost between jobs unless it is published.
- "Only first blocks count" also hides repeat 429s under a real IP-wide limit; S2 still detected it, from first contacts.
- registry.current now classifies the latest catalogs (seconds per call).
- fetches.coffees and snapshots.is_coffee are still computed at load, as unused diagnostics kept for the raw shape.
**Owner principles.**
- *Single-purpose services:* partly. Ingest, enrichment and build are separate stages (`weekly --stage ingest|enrich|build`, crawl-retry), but ingest is one omnibus job for every connector, not one per connector.
- *DRY:* yes for the HTTP client, lake, adapters and products.derive (shared by build, status and enrichment). The input_hash expression still exists twice (dbt macro and verdict.INPUT_HASH).
- *New connector = adapter + config:* no. bigcartel needs about 6 files, including models.Platform, discover.py and a limiter wired into ingest.run.
- *Versioned, tested contracts:* public (ODCS) yes. Raw is the schema-checked lake tables, tested but not versioned. There is no separate manifest/control contract: run_manifests holds roasters only, without job, connector, shard, status, counts or egress-IP refusals. Enrichment is the table schema, unversioned.
- *Manifest as control plane + Cloud Scheduler:* partly. Resume reads run_manifests, parking uses files, and the stages are chained in sequence, not triggered from the manifest.
**Cloud Run mapping.** Job `ingest` (`weekly --stage ingest --ingest-deadline-minutes 170`, timeout 240 min) → job `enrich` (`weekly --stage enrich`: enrich-pending + verdicts) → job `build` (`weekly --stage build`, the gate, publish). Cloud Scheduler: Monday ingest; Tuesday ingest `--resume-only` + `crawl-retry`; enrich and build each after their ingest, at fixed later times or chained in one Cloud Workflows execution. The owner watches exit codes, refused/parked counts, the ok share and freshness (8 days).
